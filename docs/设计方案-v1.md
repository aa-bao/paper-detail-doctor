## 四、三个值得抽象的设计模式

### 4.1 「唯一命中断言式替换」引擎

08 / 10 / 11 / 19 四个脚本表面在做四件事，实际是同一套模式：

```
读目标文件 → 对每条 (old, new) → 断言 old 恰好出现 1 次 → 替换 → 写回
（0 次 = 目标不存在，报错；≥2 次 = 可能误伤，报错）
```

这套模式的价值在于：**批量改文字时不会静默改错**。泛化后：

- `apply_edits.py --rules rules.yaml`
- 规则文件里写 `file` / `old` / `new` / `expect: 1`
- 改前自动快照到 `_backup/标题平实化前_YYYYMMDD/`（19 已有此逻辑，保留）

### 4.2 「检查项 = 检测器 + 阈值」框架

05 全稿体检的 9 项，本质是 9 个独立的 `check(files) -> list[Issue]`。
泛化成 `checks/*.py` + `verify_all.py` 后，用户可自由增删检查项、调阈值。这是让包"能长"的关键。

### 4.3 「排版期生成 vs 后处理」双模式

引注上标有两种实现路径，**互斥且各有适用场景**：

| 模式 | 适用 | 做法 | 代价 |
|---|---|---|---|
| **排版期生成** | 你有 md 源 + 排版脚本 | 排版时把 `[n]` 直接渲染成上标+超链接 | 需要 md 源；本项目走这条 |
| **后处理** | 你只有一份 docx | 打开 docx，扫描正文 `[n]` 文本，拆 run、加上标 + 插书签 + 建超链接 | 更通用，但要处理 WPS 已改写过的域代码 |

大多数人手里只有 docx，**建议两条都支持，后处理为准**（见决策 3）。

## 七、验收标准（封装后怎么算成功）

新包必须能对**一篇与本项目完全无关的论文**跑通以下链路，且不需要改任何脚本代码（只改配置）：

1. 指定论文的 docx（或 md 目录）+ 参考文献表 → 一键渲染上标引注 + 建立跳转
2. 跑引注校验 → 4 项 PASS
3. 跑全稿体检 → 输出各项 PASS/FAIL 报告
4. 跑字数统计 → 报出双口径字数与分章配额差
5. 生成/修正页眉横线 → PDF 预览中可见
